# Architecture and authorization

The API and worker share Drizzle schema and service modules. Elysia validates HTTP input and dispatches; services enforce rules using Drizzle queries and transactions. Supabase Auth supplies verified identity in Supabase mode; local mode uses PostgreSQL-backed Auth for development. Both use the same application tables. Direct PostgreSQL connections do not inherit Supabase RLS user identity. The backend never exposes Storage object keys or direct Storage URLs.

## Application composition

The layout follows the E-Commerce-BE reference: server bootstrap → application → API audience aggregators → feature route aggregators → individual Elysia endpoint plugins. `src/index.ts` starts the server with chained `.use(...).listen(...)`, without a custom stop function or process signal handlers; `src/app/app.ts` owns the `/v1` prefix and shared plugins. `src/app/dependencies.ts` creates one set of services, auth guard, and rate limiter per application. Factories accept explicit dependencies rather than opening connections at module import time, so tests, OpenAPI generation, and workers can reuse modules independently.

`src/modules/<feature>` contains descriptive service/model/repository files and audience folders (`public`, `member`, `moderation`). Routes import validation models and dispatch to services; each protected endpoint imports the same named auth guard via `.use(...)`. Its scoped `.resolve(...)` verifies credentials and adds the actor without imposing authentication on sibling public routes. Moderation services continue to require the current database moderation flag; folder names do not grant privileges. Shared request IDs, body-size checks, error mapping, and structured logs use a global lifecycle plugin, including when the API is nested in the bootstrap server.

Database schema, client, idempotency support, and seeding live in `src/infrastructure/database`; errors, common models, and HTTP helpers live in `src/shared`. Import aliases match the reference (`@/`, `@modules/`, `@infra/`, `@shared/`). Durable jobs remain in `src/jobs`, executed by `src/worker.ts`; no in-process reminder cron was added. OpenAPI generation is a script under `scripts/`.

The structural refactor preserves all 57 operations, `/v1` URLs, validation bounds, and response envelopes. OpenAPI now groups routes by feature and audience. Unmatched routes return the documented 404 error envelope rather than a generic 500. The application-error guard recognizes only domain error codes, so framework validation failures use the documented 400 response without exposing validation internals. External payloads are narrowed with runtime checks rather than unchecked casts. No schema migration, environment variable, or provider configuration change is required. The API uses normal process termination rather than custom server-draining or database-close hooks.

Regression coverage includes anonymous denial for every protected operation, standalone feature authentication without duplicate verification, public sibling isolation, nested lifecycle hooks, validation/size/404 error envelopes, and per-application rate limiting (`test/smoke.test.ts`). The isolated local integration test exercises group/challenge creation, publication, raw uploads, hidden-proof denial and reveal, password reset, moderator denial, and deletion through the HTTP plugins. The refactor passed all 59 tests, strict type checking, Biome lint/format checks, Bun build, and `drizzle-kit check`; the generated OpenAPI's operation set and request/response schemas were compared with the pre-refactor snapshot.

## Domain authorization

`memberships` records every join generation. Only one active row per group/user is allowed. Group row locks serialize invitation joins, departures, owner changes, publication, submission finalization, and sponsorship changes where needed. Publication inserts `challenge_participants` in the same transaction. `participantAccess` requires the snapshot membership ID to equal the actor's current active membership ID. `revealAccess` additionally requires an accepted, undeleted submission. Feed, attachment, comment, and reaction reads call these checks; blocks filter both directions. Previously downloaded content cannot be recalled.

Accepted proof and attachment state changes commit together. The deadline check uses PostgreSQL `clock_timestamp()` after group and challenge locks; uploading earlier does not reserve eligibility. Idempotency keys are stored with actor, operation, request hash, and result ID under a transaction advisory lock. Jobs use `FOR UPDATE SKIP LOCKED` and leases; side effects are enqueued inside domain transactions.

Cancellation and archive keep history. See [assumptions](assumptions.md) for reads and mutations. Moderator proof reads are separate from ordinary feed authorization, require the database moderation flag, require an existing report, and append an audit event. The flag must be granted only by an administrator with migration credentials; no API can self-grant it.
