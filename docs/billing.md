# Billing lifecycle

The app creates a group upgrade intent while the payer is an active member. For production, the mobile app performs a native store purchase through RevenueCat using the authenticated user UUID as RevenueCat App User ID, then calls `/v1/upgrade-intents/:id/reconcile` with the provider subscription ID. The backend fetches the payer's subscription from RevenueCat API v2 and checks customer, environment, purchase start, ownership, payment state, access, and expiry before binding it. A client `isPaid` flag or receipt string cannot grant benefits. One active sponsorship per group and one group per provider subscription are database constraints. Subscription bindings cannot self-rebind.

RevenueCat webhook delivery must enable HMAC signing. The backend checks `X-RevenueCat-Webhook-Signature` against the raw body and a five-minute timestamp window, records event IDs once, then queues reconciliation of existing bindings. Events never directly grant entitlement. Reconciliation reads current provider state, so late/out-of-order events cannot restore an expired or refunded subscription. Sandbox and production are distinct. Cancellation remains active until verified expiry; grace uses provider access state. Group members and content remain after expiry, with free limits applied to new actions.

`BILLING_MODE=test` enables deterministic local subscriptions associated with an intent; production startup rejects test mode. This is only a test adapter, not a payment flow. Production needs store products, a RevenueCat project/API key with customer subscription read permission, webhook signing secret, native purchase setup, and configured sandbox checks. Prices are set in store/provider dashboards and are not approved or represented here. See [RevenueCat subscription API](https://www.revenuecat.com/docs/api-v2/customer/resources) and [webhook HMAC documentation](https://www.revenuecat.com/docs/integrations/webhooks).
